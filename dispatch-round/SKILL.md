# 分輪派工流程

主線（本對話）負責**編排、裁示、複驗、入庫**；子代理負責**單輪的紅燈→綠燈**。
主線不寫實作碼，子代理不 commit。

> 專案特有的事實（建置指令、資料庫、平台慣例、既有陷阱）寫進**該 repo 的 `CLAUDE.md`**，
> 不要塞進本 skill。本檔只講流程；成本模型請依自己的用量記錄。

## 定調：品質第一，省錢是副產品（先讀這段，它決定了下面所有做法）

歷史上最貴的錯誤全部是**品質事故**（回報成功但沒驗證、結論建立在錯誤前提上、
平行代理互相踩掉檔案），不是 token 超支。本流程的每個裝置——事實包、複驗、對抗輪——
**首先是品質裝置**：子代理冷啟動摸索不只貴，它是代理建立錯誤假設的主要來源；
派工單寫得死，錯的空間就小。

成本模型只留四條方向性結論（成本模型請依自己的用量記錄；要自己的基準就跑 `scripts/cost-scan.py`）：

- **tokens ÷ 工具呼叫 ≈ 常數。** 成本不是「想多深」，是「翻多少檔」。
  同樣難度，派工單寫死的明顯比只給方向的便宜。
- **大部分的錢花在 context 進出，輸出只佔一小部分。** 主線與子代理的快取讀取／輸出比在同一量級
  ——子代理不是特別會「讀」，而是**每多一次工具呼叫就多付一輪整段 context**，
  所以省錢要從減少呼叫次數下手（事實包、行號錨點）。
- **長尾才是大頭。** 少數最貴的子代理吃掉大部分子代理成本，工具呼叫特別多的那一小群尤其明顯。
  探索期也不短——不少子代理在寫第一個檔之前就已經呼叫很多次工具（規劃輪、對抗輪本來就要讀完才動筆），所以熔斷不能掛在「還沒開始寫」上，
  要掛在迭代與總量上（第二節鐵律）。
- **主線不免費，而且大半花在編排的視窗裡。** 主線成本多半落在有派過代理的視窗。
  該省的是複驗時灌進脈絡的建置／測試輸出（第四節第 13 項），不是少派代理——
  少派代理就是主線自己在更大的 context 上翻檔。

結論：**把主線已知的事實寫進派工單**，同時是品質與成本的最大槓桿；
省錢的方式從來不是少派代理、砍複驗或砍對抗輪——那是把小錢換成返工的大錢。
真正的槓桿依序是：**選對層級與力度**（第三節）、**事實包與行號錨點**（第二節）、
**熔斷**（第二節鐵律）——三者都不動品質裝置。

## 一、什麼該派、什麼不該派

**派代理**：≥2 個檔案 **且** 需要自己的紅燈→綠燈循環。

**留主線自己做**（實測這樣最省）：
- 單檔測試修正、既有測試的斷言對齊
- 資料庫腳本撰寫與執行、識別碼／號碼配發
- git 操作、文件回填、記憶更新
- **所有的數字複驗**（建置／測試自己跑）。diff 審查可以另派看不到子代理回報的 reviewer（第四之二節），
  但建置與測試數字永遠主線自己跑。

**反模式**：把一輪拆成兩個小代理。輪次要併大——純機械的那種輪
（例如只是加宣告、只是對齊命名）應該併進下一輪，單獨派要付一次完整的冷啟動稅。

## 二、派工單模板

派工單的品質決定成本。**事實包不是背景說明，是省錢裝置**——
每寫一條具體事實，代理就少翻幾個檔。

```
TESTS=locked   ← 只有修正輪／只實作輪才寫這行（不寫新測試、只讓既有測試轉綠）；紅燈輪不寫
你的任務：<一句話結論式描述>。工作位置＝<絕對路徑>，分支 <name>，HEAD=<sha>。
風險等級＝<高／中／低>（判準見 ~/.claude/rules/common/testing.md）。
**不要 commit**；不開背景任務、不起服務、建置與測試前景跑完、一次交完整回報。
紀律＝先寫紅燈測試（實證紅）→ 實作轉綠。
⚠ 工作區有他方會話未提交的 <檔案>，別碰也別報告。

## 檔案集（你只能觸碰這些；含臨時檔與突變檔）
- <會新增／修改的檔>
- <驗證過程會暫時突變再還原的檔（陰性對照用）>
超出清單的需求＝停下來寫進偏差回報，不要自行擴權。

## 前情（已入庫的成果，直接用，不要重做）
- <上一輪產出的型別／方法名＋它保證了什麼>
- <已實證的事實，含具體結論而非「請自行確認」>

## 改動清單
1. **<檔案路徑>**（約 :行號）：<要做什麼>。⚠<這裡的坑>
2. ...

## 紅燈測試（新檔 <路徑>）
- <逐案列出要鎖什麼>

## 預期會紅的既有測試與處置
| 測試（含大致行號） | 處置 |
|---|---|
| <名稱> | 改寫／移除該案／維持綠靠實作滿足 |
⚠ <哪些絕對不能改，以及為什麼>

## 驗證（完工前必做）
1. <建置指令> —— 真的成功才算（見該 repo CLAUDE.md 的偽成功陷阱）。
2. <測試指令與過濾條件>：基準＝<N 案 M 紅>，完工＝<要求>。
3. 紅燈階段留輸出摘要。
4. <完工標準：只有測試綠，還是要含真實環境實證？主線明講，不寫＝主線的漏>
5. 回報：檔案與區塊、紅→綠證據、測試四數字（總數／綠／紅／略過）＋失敗名稱全列、
   盤點類任務附**實際執行過的搜尋指令**、**與派工單的偏差逐筆**。

## 鐵律
- **熔斷 A（迭代）**：同一個建置或測試指令**連跑三次仍紅**，停下來回報——
  每次改了什麼、每次紅的名稱集合、你認為缺的事實在哪。不要換第四種假設。
  （實證紅燈那一次是預期結果，不算；從開始轉綠算起。）
- **熔斷 B（總量）**：工具呼叫累積達 **100 次**仍未完工，停下來回報進度與剩餘項目。
  主線補事實包後重派。**到 100 就停，即使只差一步收尾**——差一步的那份由主線補，比你多跑 30 次便宜。
- <專案級不可違反的事項>
```

**必寫的四段**：
- `前情`——免得代理重新發現主線已知的事
- `改動清單的行號錨點`——每一條都要指到檔案與大致行號。成本正比於工具呼叫次數，
  而沒有錨點的代理要自己翻檔**重新發現主線已經知道的位置**：同難度的兩輪，
  派工單寫到行號的那輪，工具呼叫次數與 tokens 都明顯少於只給方向的那輪。
  行號錨點不是體貼，是把那些呼叫省下來的直接手段。
  原本只有規劃輪被要求產出檔案地圖（第六節），實測顯示每一種輪型都有同樣的重複發現問題。
- `預期會紅的既有測試`——免得代理以為是自己弄壞的，然後花大量 token 去「修」
- `偏差逐筆`——代理的判斷往往是對的（它看到你沒看到的事實），但主線必須知道

**風險等級高的案子，模板的「紀律」那行要拆成兩輪。** testing.md 規定高風險的測試不能由寫實作的人寫，
而模板預設是同一個代理先寫紅燈、再實作。高風險時改成：紅燈輪（主線或另一個代理只寫測試，實證紅）→
只實作輪（第一行標 `TESTS=locked`，刪掉「紅燈測試」段，改寫「紅燈測試已入庫於 <路徑>，讓它們轉綠」）。
只實作輪的「紀律」改成「不新增、不修改測試，只改實作讓既有紅燈轉綠」；熔斷 A、B 照用，
這種輪紅燈已入庫，熔斷 A 從第一次跑測試就開始算。

**`TESTS=locked` 是機制，不是叮嚀。** 寫程式的代理最便宜的轉綠方式是把斷言改鬆，
派工單寫「不要改測試」擋不住。標了這行，`~/.claude/hooks/test-edit-guard.sh` 會在
PreToolUse 擋下它對測試檔的 Write／Edit（只認派工單**第一行**是 `TESTS=locked`，內文提到不算）；沒標的子代理改測試檔也會記到
`~/.claude/logs/test-edits.jsonl`，供複驗第 8 項對帳。
「預期會紅的既有測試」表裡處置是「改寫」的輪次不能標 locked——把改測試拆給主線或另一輪做，
讓寫實作與改測試不是同一個代理。

**熔斷條款不是省錢裝置，是品質裝置。** 一個同一條測試連紅三次還在換假設的代理，
它建立的假設幾乎一定是錯的——讓它跑完只是把錯誤堆得更高。最貴的單一子代理
可以花掉中位數的幾十倍；重派一次的成本遠低於讓它跑完。

⚠ **熔斷 B 只寫門檻擋不住越線。** 派工單只寫「100 次停下」時，代理仍會越線；
在鐵律段多一句「到 100 就停，即使只差一步收尾」並點名前例後，就守住了。
模板已含這句，**派工單照抄、不得刪**。

⚠ 兩個閾值的來源：舊版寫「40 次未進紅燈就熔斷」，不少子代理在第 40 次呼叫時
還沒寫第一個檔（規劃輪與對抗輪本來就要讀完才動筆）——那條件會**誤殺正常的讀取型輪**。
總量 100 只會碰到少數子代理，卻切在吃掉大量成本的長尾上，
不碰大多數正常代理。成本模型請依自己的用量記錄。
用第四節第 7 項的紀錄持續校準：正常的代理也常撞到就往上調，長尾還是漏出來就往下調。

## 三、模型分層

**預設是中階，高階是例外。** 分層判準寫成表格但沒有預設值時，趕進度的人一律會選最強的
（子代理成本會大量落在高階）。角色檔繼承主對話模型後，**「不指定」等於「跟主線一樣高階」**，
所以派工單層的預設值比以前更重要：

> 派工單的 `model` 欄**預設中階**。要用高階，必須在派工單裡寫一行理由
> （具體指出哪一步需要取捨判斷）。**沒寫理由＝用中階。** 規劃、對抗、盤點三種輪型免寫理由。

層級**相對於主線定義**，不寫死型號——換代就不用改表：

| 層 | 定義 | 2026-11 對應 |
|---|---|---|
| 主線 | 你的主對話模型 | Opus 5.5 |
| 子代理高階 | 低主線一級的當代旗艦；主線已是該級時取同級 | Opus 5.5（＝主線同級） |
| 子代理中階 | 再低一級 | Sonnet 5.5 |
| 瑣碎 | 最低階，只給格式對齊、批次改名這類 | Haiku 5.5 |

⚠ **主線與高階同級時，「主線比子代理高一級」的落差消失**——規劃、對抗的結論由同一個模型產出
又由同一個模型裁決，盲點相關（對策見第四之一節「時機」）。Agent 的 `opus`／`sonnet` 別名會跟到該級
最新版，不必改派工單；要異質模型時對抗輪明寫 `model: fable`。

| 任務性質 | 層 | 依據 |
|---|---|---|
| 規劃輪、對抗輪、**盤點／調查／守衛補完** | 高階（免寫理由） | 結論會流進下游，錯了要整串返工；對抗輪降中階，含部分推翻率明顯下降 |
| 有裁示含量的實作、跨檔重構 | 高階（要寫理由） | 要推理與取捨 |
| 機械性宣告、測試 fixture 對齊、跑基準線、格式對齊 | 中階 | 用量明顯較少，完成度沒有差別；新模型組合待重測 |
| 既有測試斷言對齊、照改動清單逐條實作 | 中階 | 事實包夠死的話不需要高階 |
| 改動測試載具（fixture、替身註冊、測試身分、worktree 隔離）且派工單給不到載具行號 | 高階（理由寫「載具錨點不足」） | 中階長尾集中在這類單，見下方 ⚠ |

⚠ **中階的長尾集中在測試載具類單。** 中階超過 100 次的單，多半是動測試載具或缺資料庫錯誤碼實際值的；
高階少很多。派中階的條件仍是「事實包夠死」：載具的替身形狀與 fixture 行號給得出來就派中階，
給不出來就升高階或先補事實包。另中階代理**自報的呼叫次數會低報**——
複驗第 7 項一律讀 Agent 結果的數字，不看代理正文。

⚠ **降階只降「機械操作」，不降「事實判斷」。** 盤點／調查／守衛補完的產出是事實判斷，
它們正是第四之一節要求預設跟對抗輪的三種輪型——降階降的是代理建立正確假設的能力，
而那是本流程開頭說的「最貴的錯誤」的來源。成本上也未必划算：盤點品質下降會推高
對抗輪推翻率進而返工，省下的模型價差遠不夠賠。

**模型與力度怎麼決定**：

- 子代理模型的決定順序：派工單 `model` 參數 → 角色檔 frontmatter `model` →
  環境變數 `CLAUDE_CODE_SUBAGENT_MODEL` → 主對話模型。**派工單參數永遠優先**，
  所以分層只在派工單上明講。
- `.claude/agents/*.md` 的角色定義**不釘 model**（2026-09 起已全部移除），讓角色繼承主對話模型，
  避免主模型升級後子代理還卡在舊模型。
- **力度（effort）**：機械性任務派工時帶 Agent 的 `effort` 參數（本 skill 明定：機械輪用 `medium`），
  或在角色檔 frontmatter 設，比只降模型再省一截，完成度實測無差；規劃與對抗輪維持主線力度，不帶參數。

⚠ **同一級之內也要挑版本。** 快取讀取是成本大宗，而同級的不同版本快取費率
可能差好幾倍——舊版旗艦即使訊息數只多一些，成本也可能高出許多，
差額全部出在快取費率。**選的是「這一級裡最新的那個」，不是「用順手的那個」**；
同級後繼版本換過去沒有品質風險，純粹是價差。每次換代後重新確認一次現行費率，
並更新 `scripts/cost-scan.py` 頂端的定價表。派工單裡若還寫著舊版型號，一樣要換掉。

## 三之一、平行派工（兩個以上代理同時跑時，逐條檢查）

平行的風險不是多花錢，是**互相踩掉對方的產物讓結果變錯**。一條前置、四條鐵律，全部來自實際撞車：

0. **先定介面，再平行。** 規劃輪先把共用介面／registry／型別寫好並 commit，
   再把檔案歸屬寫進 `implementation_plan.md` 的 ```ownership 區塊（格式見第六節）。
   平行代理只能動分給它的 glob；`shared:` 的檔誰改都算越界。
   不是靠派工時人工比對「檔案集」，是複驗時跑 `check-ownership --agent <名> --base <分岔點>` 機器核對
   （exit 3＝越界退回；exit 2＝計畫根本沒歸屬表，不能當通過）。
   做法來自〈Made by mechanical means〉：每卷帶子一個檔、統一 `mount／frame／input／stop` 介面，
   thread 才能同時做而不互踩。
1. **檔案集不相交才准平行。** 比對的是各代理派工單的「檔案集」欄——
   **臨時突變檔也算**（兩個代理各寫各的測試檔，但陰性對照都會突變／還原同一個
   production 檔，就會互相 `git checkout` 踩掉對方）。有交集就串行，不要賭。
2. **平行代理禁用 `git stash`。** stash 是全 repo 共用（worktree 也共用 refs/stash），
   會互彈。紅燈備份改 patch 法：`git diff > backup.patch` → 還原時 `git apply`。
3. **代理運行中，主線要 commit 必須帶路徑**（`git commit -- <paths>`），
   否則會吞掉代理已 staged 的變更。
4. **代理還在讀的目錄，主線不 commit 也不改檔**——連「只讀」的 reviewer 也一樣。
   主線要準備下一輪的素材（例如修正 commit），就另開副本。2026-10-26 實測差點汙染
   第一輪 review（主線在 reviewer 讀檔途中 commit 了第二輪修正）。

代理可能留下中間產物：**收工前主線跑 `git status` 掃殘檔**，殘檔差點被部署出去是真實案例。

## 三之二、背景任務與長指令（渲染、長建置、跑很久的腳本）

模板預設「不開背景任務」。指令會超過工具逾時才例外，派工單要明寫：怎麼跑、輸出到哪、怎麼判定完工。
下面五條來自 2026-11-02 的事故：渲染早已失敗，5 小時沒有人發現。

1. **不能只等通知。** 代理可能漏接「背景任務結束」通知而空等，主線也可能等一個不會來的回報。
   代理開了背景任務就要自己定時查；主線派出時定好查核時間，時間到直接看程序與輸出檔，不靠代理回報。
2. **監看要能判定失敗，不是只等程序結束。** 「程序消失」不等於完成：
   程序消失且沒有輸出檔＝失敗；log 命中錯誤字串＝失敗；輸出檔存在、log 乾淨、程序結束才是完成。
3. **`pgrep -f` 會比對到監看腳本。** 監看迴圈的命令列本身就帶目標字串：Linux 會比對到自己；macOS 預設排除
   自己與祖先程序，但另一個監看迴圈（例如另一個代理開的）照樣會中，程序永遠「還在跑」。
   一律寫成 `[n]ode_modules` 這種括號形式——它比對得到目標，但比對不到寫著括號的命令列。
   所有監看腳本都要這樣寫，留一個沒括號的，其他的就會比對到它。
4. **長渲染分段跑。** 每段可獨立重跑、各自輸出檔案，最後才合併；單次失敗只重來那一段，不是整支。
5. **派工後才追加的需求，代理可能還在跑舊版。** 追加後要求代理回覆「現在跑的是哪一版、參數是什麼」，
   沒回覆就當沒讀到。舊輸出當檢查點保留：輸出檔名帶版本，不要覆蓋；複驗時確認交來的是新版。

```bash
# 確認程序已經啟動後才開始監看，否則迴圈會立刻結束、誤判失敗
while pgrep -f '[n]ode_modules/.bin/<工具>' >/dev/null; do
  grep -qE '<錯誤字串>' "$LOG" && { echo FAILED-log; exit 1; }
  sleep 30
done
grep -qE '<錯誤字串>' "$LOG" && { echo FAILED-log; exit 1; }
[ -s "$OUT" ] || { echo FAILED-no-output; exit 1; }
echo DONE
```

## 四、主線複驗清單（每輪；不採信子代理自報數字）

```
1. git status --short     # 對帳：只該有派工單「檔案集」列的檔
2. git diff 審查關鍵區塊   # 尤其確認「不該動的地方」真的沒動
3. 自己跑一次建置
4. 自己跑一次測試          # 比失敗名稱集合，不比數量
5. 每 2~3 輪跑一次全量      # 抓跨輪漂移與本案外的既有缺陷
6. 突變抽驗 1~2 條新測試    # 暫時弄壞它鎖的實作 → 確認真的紅 → 還原 → 確認回綠
7. 讀代理的工具呼叫次數      # Agent 結果附 totalToolUseCount（背景通知為 tool_uses）；>100＝事實包不足，下輪補
8. 測試檔對帳              # git diff --stat 測試檔 + ~/.claude/logs/test-edits.jsonl 本輪紀錄，
                           # 每一筆都要對得上派工單「紅燈測試」或「預期會紅」表，對不上＝退回
                           # lock_check=missing＝hook 找不到子代理紀錄、沒能判斷是否鎖定，該筆要人工查
9. 獨立 review（中／高）    # 收官前派一個沒有本對話脈絡的 reviewer（見四之二），主線自己重讀不算
10. risk-paths --base <分支> # repo 有 REVIEW.md 才跑；命中＝高，對照派工單的風險等級
11. check-ownership --plan implementation_plan.md --agent <名> --base <分岔點>
                           # 平行輪才跑，每個代理各跑一次；exit 3＝越界退回，exit 2＝沒歸屬表＝規劃輪的漏
12. 爬分輪：自己重量指標 + git diff --stat 基準圖／門檻檔必須為空
                           # 代理不准更新基準圖或放寬門檻；細則見 references/hill-climb.md
13. 建置／測試輸出過濾再進脈絡 # 只留失敗名稱與四數字摘要，全文寫到檔案再 grep
14. 長指令輪：輸出檔親自核對  # 檔案存在、是新版、大小與時長合理（第三之二節），不看代理的「已完成」
15. 終檢修正的閉環          # 終檢列的「重要」修完後，原檢查員只複檢那幾項與接縫；主線抽樣不能代替
                           # 畫面類產出（影片、截圖、簡報）再用 OCR 全掃敏感字串（折扣碼、email、邀請碼、金鑰）
                           # 含問題的舊輸出改名或刪除，不留在交付目錄
```

第 5 項最容易省，但它是抓「別的地方壞掉」的唯一手段——
實例：某輪全量跑才發現一個與本案無關的授權歸類遺漏（前一天的 commit 留下的）。

第 6 項驗的是**測試本身鎖不鎖得住**——全綠可以是空鎖。抽驗優先挑本輪最核心的斷言。
⚠ 陰性對照「該紅卻綠」時，**先查建置環境再懷疑測試**：檔案鎖造成的假建置、
增量建置跑到還原前的舊組件，兩者都會讓突變驗證的數字全錯（見該 repo CLAUDE.md）。
還原後要確實觸發重建再跑。

第 8 項防的是「測試被改到配合實作」。hook 只攔得到 Write／Edit，
代理用 Bash 的 sed 或重導向改測試不會留紀錄，所以 `git diff` 那一半不能省。

第 15 項防的是「修了，但沒人確認修好」。實例：終檢抓到影片截圖露出折扣碼，製作代理蓋掉後重渲，
主線只抽 4 幀目視就放行；檢查員沒有複檢，也沒人全片掃字，含問題的舊版還留在輸出目錄。
修正輪交件時三件缺一不交：原檢查員複檢、OCR 全掃、舊輸出移出交付目錄。

第 7 項是**派工單品質的唯一回饋訊號**，而且不必手抄——Agent 工具的結果本來就附
`totalToolUseCount` 與 `totalTokens`，背景代理的完成通知附 `tool_uses` 與 `subagent_tokens`。
超過 100 次就在裁決時標記「事實包不足」，把缺的事實補進下一輪的「前情」。
沒有這個訊號，派工單品質永遠停在憑感覺，而長尾正是從這裡長出來的。

第 13 項是主線側最大的可壓項。主線每則呼叫帶的 context 很大，其中大半是複驗時
整份建置與測試輸出灌進來的；主線之後每一步都在為那些行付快取費。

複驗每輪花費很少，**是全場投報率最高的支出，不要省**。

### 偏差裁決（複驗的一部分，不是選配）

代理回報的每筆偏差，主線必須**逐筆給出去向**：
- **採納**——寫進下一輪派工單的「前情」，成為正式事實；
- **退回**——開修正輪或主線自己修，不能只在心裡記著。

不允許默默放過：沒裁決的偏差會讓下一輪的前情建立在含糊狀態上。
另外，**引用前輪結論當前提之前先驗前提**——守衛檔頭、Skip 理由、
裁定紀錄裡引用的「事實」可能已過期或當初就是錯的，被引用不等於還成立。

## 四之一、對抗輪（品質槓桿第一名）

盤點、調查、守衛補完這三種輪型的產出，**預設必須跟一輪對抗式查證**——
另派一個代理，任務是**推翻**前一輪的結論，不是複述或補充。
對抗輪推翻或部分推翻前一輪結論的情況並不少見，且推翻經常反轉結論；沒有對抗輪，錯誤結論會直接流進實作。

- **時機**：前一輪的結論會被後續輪次依賴時，以及**風險等級為高**的實作輪（金流、資料遺失、
  對外發送、權限、正式部署）——對抗代理的任務是找出「測試沒碰到的情境」，
  不是重跑既有測試。純機械輪（宣告、對齊）不用跟。
  🔴 **主線與規劃代理同模型時，規劃輪預設也要跟**——結論由同一個模型產出、又由同一個模型裁決，
  主線的親查抽驗抓不到同源盲點。實例：某案四個規劃輪全數沒有對抗，對抗輪反而派在已被測試與突變
  鎖住的結算輪上（一條都沒推翻）——對象選反了。跳過規劃輪的對抗要留理由，理由不能只是「主線已親查前提」。
- **結算輪的對抗**（全量後對已入庫實作做不變式查證）是選配：對象已被測試與突變抽驗鎖住，推翻率先天近 0，
  價值在**順手發現**。做的話紀錄寫「推翻 n／m＋順手發現屬實 k」，不要拿來比較模型的推翻率。
- **派工單寫法**：把待推翻的結論**逐條列出**、附原始證據位置（檔案與行號），
  要求對抗代理對每條給「成立／推翻＋獨立證據」——它必須自己重新查證，
  不得沿用前輪的搜尋結果。逐條列出也讓這輪成本壓到接近下限。
- **裁決**：推翻的條目由主線裁決後更新結論與後續派工單；
  對抗輪自己的斷言同樣要附搜尋指令與證據，主線抽查。
- **跳過**：主線可裁示跳過，但必須在紀錄裡留一行理由（例如「結論不進入後續依賴鏈」）。
  不留理由的跳過視同流程違規。
- **使用情境規格（審 UX 產物時必加）**：對抗的對象是畫面或流程（新頁面、走查清單、微文案）時，
  對抗代理**不以開發者視角讀碼**，而是照一組情境條件從入口操作到終點。情境規格**只准五項**：
  權限組合／裝置寬度／入口／任務起點與終點／資料量——**不寫**使用者的心理、記憶、熟練度或感受
  （AI 無從驗證，寫進去會被當成證據）。產出分「任務中斷點」與「做得完但路徑繞遠」兩欄，
  每條附獨立證據（截圖、操作步驟或 grep），不得沿用前輪的結論。
  🔴 **證據等級**：AI 的產出一律標「檢查發現」（畫面有／無某性質），不得寫成「使用者會…」；
  好不好用、看不看得懂、想不想用**只接受真人測試資料**，對抗代理只能把這類疑點列為「待真人測試」。
  情境清單寫在該 repo，不塞進本 skill。
  （原「使用者 persona」寫法作廢——具名 persona 的心理描述會被下游當成證據。）

## 四之二、獨立 review 與收斂

規則本體（分級標籤、回報格式、收斂上限）在 `~/.claude/rules/common/code-review.md`，這裡只講派工。
對抗輪推翻的是**某條結論**；獨立 review 看的是**整個 diff**，兩者不互相取代。

- **reviewer 派工單只給四樣**：repo 路徑、base／head SHA、PR 意圖（一句話＋規格）、
  repo 的 `REVIEW.md`。**不給**主線的推理與實作經過——給了就繼承同樣的盲點。只讀不改。
  派工單要明寫「被改到的檔整份讀，不只看 diff」：2026-10-26 實測規則只靠自動載入時，
  reviewer 只讀 diff、既有問題 0/2；派工單明寫時 2/2。
- **修正輪只接「重要」**：小意見與既有項由主線記進待辦，不派代理去修
  （代理會把每則小意見都修掉，每修一次多一個 commit 和一輪 review）。
  同類 bug 要求修掉 reviewer 列出的全部實例，不是只修被點名的那一行。
- **第二輪起**：reviewer 只看 `git diff <上輪 head>..HEAD`，派工單附「已提出的發現」清單，不得重提。
- **第三輪後仍有重要項＝熔斷**：停下來，主線（必要時問 Dex）重想做法，不派第四輪。
  理由同第二節熔斷——一直修不收斂，通常是做法錯了，不是修得不夠。

2026-10-26 用預埋 bug 的 fixture 對照新舊規則實測，數字見 `references/review-eval-2026-10-26.md`。

## 五、入庫紀律

- **測試綠≠完工。** 涉及畫面或整合面的輪，完工定義要多一條「真實環境目視／
  端到端實證一次」——視圖解析、樣式缺祖先、組態靜默取預設值這類缺陷，測試層抓不到。
  含不含實證由主線在派工單裡明講（模板驗證第 4 項），不寫就是主線的漏。
- 程式碼與文件**分兩個 commit**
- commit 訊息寫「為什麼」與「實測數字」，不只寫「做了什麼」
- 子代理不 commit；主線複驗後才 commit
- **每輪複驗過就立刻 commit，不要累積到收官**——session 可能隨時中斷，
  未入庫的綠燈等於沒發生
- 被 gitignore 的專案文件要 `git add -f`（各 repo 情況見其 CLAUDE.md）

## 六、規劃輪的特殊要求

- 產出必須含**檔案地圖（含行號錨點）**，讓實作代理直接信任、不重讀。
  否則規劃讀一次、實作再讀一次，同樣的檔付兩次錢。
  （行號錨點現在是**所有**派工單的必寫項，見第二節「必寫的四段」；
  規劃輪的特殊之處在於它要產出的是整案的地圖，不只是本輪要動的那幾行。）
- 回報末尾要有「待裁示事項」，且每項**給明確建議而非開放式選項**。
  主線照「例行判斷自己下」的原則裁掉，只有真正改變方向的才回問使用者。
- **下一輪會平行派 ≥2 個代理時，必須產出「介面與檔案歸屬表」**，寫進 `implementation_plan.md`：
  共用介面（型別、registry、設定）先由規劃輪或主線寫好 commit，代理只讀不改；
  每個代理擁有哪些 glob 要不相交。格式固定，給 `check-ownership` 讀：

  ````markdown
  ## 介面與檔案歸屬（平行輪）
  共用介面已 commit 於 <sha>：`src/tapes/types.ts`（`mount／frame／input／stop`）。
  ```ownership
  shared: src/tapes/types.ts         # 共用檔：主線先 commit，代理只能讀
  shared: src/tapes/registry.ts
  tape-notion: src/tapes/notion/**   # 名稱: glob，一行一個；結尾 / ＝整個目錄
  tape-slack: src/tapes/slack/
  ```
  ````
  規劃時先跑 `check-ownership --agent <名> --files <它要動的檔>` 確認分法對得上改動清單；
  複驗時用 `--base <分岔點>`（第四節第 11 項）。沒有這個區塊就不准平行派工。
- 爬分類的案子（Lighthouse、bundle、測試時間）另有做法與派工單，見 `references/hill-climb.md`。

## 七、什麼時候該改開新對話

不是「換一輪」，是**換一個案子**：不同子系統、不同裁示脈絡，
或中間有真實的人類檢查點（隔天、等對方回覆）。

同一案拆成多個對話會付兩份稅：交接文件的撰寫與閱讀，
加上**跨輪強制力消失**——基準線紀律、裁示前後一致、號碼不撞號，這些都靠同一個上下文記著。
實例：某案的交接文件寫得很完整，接手方仍推翻了其中兩條技術判斷（文件會過期）。

### 換視窗的時機判斷（主線每輪收官後自問一次）

判準是「**下一段工作需不需要這裡累積的脈絡**」，不是「累積了多少」。
同一視窗有 prompt cache，重送前綴便宜；真正的浪費是帶著用不到的脈絡做別的事。

| 情境 | 動作 |
|---|---|
| 本案收官（commit＋文件＋記憶都更新完），下一件事無關 | **提議換**——此刻交接成本已經付掉了 |
| 使用者轉向別的案子／子系統 | **提議換** |
| 工作要繼續但已接近自動摘要 | **提議換**——與其被摘要掉細節，不如趁文件還準確時主動交接 |
| 同一案的下一輪 | **不換**——跨輪強制力比省下的 token 值錢 |
| 等子代理回報中、複驗做到一半 | **不換** |

**換之前必做**（換視窗或換主線模型都一樣）：確認交接文件（HANDOFF、PROGRESS、記憶，各 repo 叫法不同）是最新的，
並明講新視窗第一句該讀什麼。交接文件不準時不要換——那只是把成本推給下一個視窗。

⚠ 收官點是最省的切換點，因為那裡的交接文件本來就得寫。
在輪次中途換視窗要額外寫一份「臨時交接」，那是純虧。
