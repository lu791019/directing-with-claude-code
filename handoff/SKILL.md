# HANDOFF 規則與範本

> 2026-10-15 依 5 個專案（散場誌、練功房、blog 與另外兩個個人專案）共 11 份交接檔整理，Dex 確認。
> **讀者是決策者**（Dex、客戶、接手的人或 agent）：上半部讓人 1 分鐘內看懂現況、要決定什麼、有什麼風險；技術細節放下半部或連到別的檔。

## 一、寫什麼
1. **起手指令（第一段）**：列出讀完本檔後接著要讀的檔（最多 3 份），寫檔名不寫內容。本檔自己靠開場的 `@HANDOFF.md` 帶進來，不靠這行字（見第六節）。快照式另寫「上一份是哪份、本份涵蓋哪段期間」。
2. **一句話現況**：正式環境版本（revision／commit）＋這一輪做完什麼，一兩句。
3. **等你拍板**：每條附建議答案與「不回覆時的預設」，標 `[待確認]`。拍板後就刪掉或移到「已拍板」。
4. **本期上線**：每次部署一條，寫版本、做了什麼、怎麼驗收（測試數字、在正式站實測了什麼）。
5. **下一步**：依優先序；標明哪些是 Dex 要親手做的（建帳號、送審、輸入憑證）。
6. **坑與事故根因**：只寫會再踩的；寫「症狀 → 根因 → 怎麼避免」，不寫排查過程。
7. **環境與部署**：服務在哪、怎麼部署、每月成本；指令只放驗證過的。
8. **憑證**：只寫「存在哪裡、誰有權限、何時輪換」，見第四節。

## 二、不寫什麼（放別處，HANDOFF 只連過去）
- 逐項進度與勾選 → `task.md`
- 規格、架構、設計理由 → `implementation_plan*.md`、需求檔、grill 紀錄
- 逐檔改動、commit 訊息、重構、雜務、lint 警告、個別測試名稱 → git log
- 失敗的嘗試與排查過程（除非變成「坑」）
- 跨專案的工作紀律 → `CLAUDE.md`
- **任何金鑰、密碼、token、邀請碼的值**

## 三、什麼時候開新檔或封存（任一條成立就做）
| 觸發 | 做法 |
|---|---|
| 活檔超過 **150 行**或 **25KB** | 已完成、已拍板的段落移到 `HANDOFF-封存-YYYY-MM-DD前.md`，封存檔開頭寫「僅供查歷史，現況以 HANDOFF.md 為準」；活檔只留現況、待拍板、下一步、仍有效的坑 |
| 單一條目超過 **500 字** | 拆成子條，細節移到 task.md 或 walkthrough，只留結論與連結 |
| **換階段**（里程碑結束、交付客戶、換機器或換人接手） | 開新快照 `HANDOFF_YYYY-MM-DD.md`，頭部連到上一份並寫涵蓋期間；舊檔不再改 |

（門檻依練功房 10/12 在約 123 行、23KB 時拆檔的經驗訂定，可再調。）

## 四、憑證交接（客戶專案、demo 帳號）
- 值一律不進 HANDOFF、不進 git、不貼在對話裡。交付走密碼管理器的共享項目、雲端的密鑰管理服務，或面交。
- HANDOFF 只寫一張表：

| 項目 | 用途 | 存放位置 | 誰有權限 | 建立日 | 輪換或失效日 |
|---|---|---|---|---|---|
| 例：demo 管理員帳號 | 客戶驗收 | 密碼管理器「〇〇交接」共享資料夾 | Dex、客戶窗口 | 2026-08-17 | demo 結束後 3 天內輪換 |

- 交接後在 HANDOFF 記「已交付給誰、哪天、輪換了沒」。

## 六、新 session 怎麼讀
- **開場訊息用 `@HANDOFF.md`**（例：「@HANDOFF.md 繼續」）。@ 會把全文帶進 context；只用文字說「先讀 HANDOFF」時，檔案要等 Claude 決定打開才看得到——10/16 掃描：148 個提到 HANDOFF 的 session 只有 9 個真的打開。
- **用文字叫讀時（退路）**：Claude 回覆前必須先用 Read 打開全文，不可只憑檔名、摘要或記憶作答。
- 檔案超過 150 行或 25KB 時先依第三節拆檔，避免 @ 一次帶入過多內容。
