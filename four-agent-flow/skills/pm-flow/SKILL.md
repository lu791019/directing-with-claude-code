# pm-flow：需求分析三步

把需求文件變成「大家對同一件事有同樣理解」的驗收情境。三步照順序做，不跳。

## 開工前：讀 PROJECT_PROFILE.md

專案根目錄放一份 `PROJECT_PROFILE.md`，寫清楚：

- 需求文件放哪、PM 產物放哪（下文叫 `{PM產物目錄}`）
- 領域名詞表（產出一律沿用這些詞）
- 流程開關：grill 要不要強制、要不要產給客戶回填的規格頁

沒有這份檔、或欄位空白，先問使用者，不要猜。欄位寫「（無）」是合法答案。

已經有先前的產物（事件風暴、`.feature`、grill 紀錄），以檢查、沿用為主，不從零重做，交件時寫明沿用了哪些。

## 第一步：事件風暴

輸出 `{PM產物目錄}/event-storming-{功能}.md`。四種元素：

| 元素 | 怎麼命名 | 例子 |
|---|---|---|
| Domain Event | 過去式 | 訂單已建立 |
| Command | 祈使句 | 建立訂單 |
| Aggregate | 業務名詞 | 訂單 |
| Policy | 「當…則…」 | 當付款完成，則寄出收據 |

另加一張**畫面清單**：畫面名稱、用途、怎麼開（彈窗／跳頁／同頁展開，三選一）、對應哪個事件或命令。

- 每一格都要有出處。查不到寫「❓ 待確認」並開一題 `Q-XX`，不要填一個看起來合理的答案。
- 每個 Domain Event 都要對得到畫面；對不到就是漏了畫面，或它是純後端（明寫出來）。這一步最能抓到「驗收條件被悄悄縮水」。

## 第二步：grill 質詢輪（預設強制）

事件風暴寫完就自動進入，不問「要不要質詢」。

- 對象是**文件寫得不夠細、但會影響做法的地方**：值域、預設值、衝突怎麼處理、舊資料怎麼相容、權限、錯誤時畫面怎麼說。
- 一次問一批，每題給選項與建議；回答拍板的寫進 `{PM產物目錄}/grill-{主題}.md`。
- 拍板的領域用語，當場補進 PROJECT_PROFILE 的名詞表。
- 要客戶或 PO 決定的題標「已轉單」。沒拍板的題，不准用建議答案當定稿。

## 第三步：業務版 Gherkin

輸出 `{PM產物目錄}/{功能}.feature`。

- 關鍵字用英文（Feature、Scenario、Given、When、Then…），描述用專案主要語言。
- 一個 Feature 對一個業務範圍；一個 Scenario 對一條完整流程或一個邊界情境。
- 多組資料用 `Scenario Outline`。
- grill 拍板的結論直接寫進情境；還沒拍板的標 `[待確認]`，不寫成定稿。

```gherkin
# language: zh-TW
Feature: {功能名稱}
  作為 {角色}
  我希望 {目標}
  以便 {價值}

  Scenario: {正常流程}
    Given {前提}
    When {動作}
    Then {可觀察的結果}

  Scenario: {異常流程}
    Given {前提}
    When {錯誤的動作}
    Then {錯誤時看到什麼}
```

## 交件前自己對一次

- [ ] 每個 Command 至少對到一個 Domain Event；每個 Domain Event 至少對到一個 Scenario
- [ ] 有異常情境：資料不合法、權限不足、狀態衝突
- [ ] 每條 Policy 都有自己的 Scenario
- [ ] 畫面清單的「怎麼開」都填了，事件都對得到畫面或註明純後端
- [ ] grill 紀錄已存；`Q-XX` 編號和 grill 紀錄共用一組
- [ ] 列出「待推翻清單」交回主線：範圍邊界、值域、每一條驗收條件，各附依據位置。要不要派對抗輪由主線決定
- [ ] 交件摘要寫：產物路徑、還沒回覆的 `Q-XX` 與要等誰、補進名詞表的用語
