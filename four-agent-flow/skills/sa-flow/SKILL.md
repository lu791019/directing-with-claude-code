# sa-flow：系統分析三步

PM 寫的是「要什麼」，SA 要把它對到「這個專案實際上有什麼」，寫成工程師不用再猜的規格。

## 開工前

讀 `PROJECT_PROFILE.md`：技術棧（決定要掃哪些維度）、測試方式、程式碼根目錄、`{PM產物目錄}`、名詞表、流程開關。缺欄位先問。SA 產物預設放 `{PM產物目錄}` 旁邊的 `sa/`。

全部讀過：PM 的 `.feature`、事件風暴（含畫面清單）、PM 的 grill 紀錄、客戶回填檔（有的話，回填內容優先於原始規格）。

PM 那一棒有沒回覆、又會影響設計的 `Q-XX`，停下來列題號，不要假設答案。

## 第一步：掃描

輸出 `sa/scan-{功能}.md`，每列：元素｜這次拿來做什麼｜既有或新增｜證據（檔案:行號）。

**每個專案都掃：**
- 專案的 CLAUDE.md、ADR、名詞表——已拍板的決定不重問，要偏離就列進質詢輪。
- 相似功能：這次的每個畫面、每支 API，都要指定「照哪個既有檔案的寫法」，再逐條列差異。找不到相似的，就是新做法，進質詢輪。
- 命名與目錄慣例。

**有前端時：** 路由與守衛、選單、既有頁面型態（清單、明細、表單、彈窗）、共用元件（打開檔案確認 props，不猜）、API 呼叫層、全域狀態、格式化工具、防重送與二次確認這類既有防呆。

**有後端時：** 分層與模組歸屬、既有端點與分頁慣例、DTO 命名、驗證機制與**固定錯誤碼**、權限、多語系、併發控制（樂觀鎖等）。

**有資料庫時：** 相關資料表的實際結構；舊資料長什麼樣要用**唯讀連線實查**，不寫「應該沒有」。任何寫入都要使用者明確同意。

掃完要答得出：各維度找到幾個、每個畫面／端點照誰的寫法、每個失敗情境的錯誤碼查不查得到、哪些 PM 要的東西專案裡沒有。

## 第二步：設計 grill 質詢輪（預設強制）

掃完、寫任何 `sa/*.feature` 之前自動進入。SA 之後就開工了，沒拍板的設計會直接變成實作者的假設。

- 問的是**設計決定**：架構選擇、模組放哪、前後端介面欄位、資料表要不要改、和既有慣例衝突的地方、錯誤怎麼回。
- 舊資料相容先查資料再問。
- 紀錄寫 `sa/grill-{主題}.md`；`Q-XX` 從 PM 那邊最大號接著編。

## 第三步：技術版 Gherkin ＋ 技術設計

### `sa/{功能}.feature`

逐畫面判斷型態：清單查詢、明細與狀態操作、表單建立編輯。硬規則：

1. **技術名稱只能來自掃描表。**
2. UI 情境的 Then 只寫畫面看得到的結果；API 情境才寫狀態碼與回應內容。前後端都有的功能，兩層都要寫（`@api`、`@e2e`）。
3. `@e2e` 情境用畫面上的文字描述操作，不寫 CSS selector。
4. 每個失敗情境標既有錯誤碼，Then 寫使用者看到的文案。查不到的錯誤碼不自己編，開 `Q-XX`、先標 `[待確認]`。
5. 會寫資料的操作，都要附防呆情境：防重送、破壞性動作的二次確認、同時編輯的衝突——用專案現有的機制描述，沒有就是設計缺口。
6. 檔頭寫：來源 PM feature、型態、對應的實際檔案。
7. 檔尾附「錯誤碼 × 觸發情境 × 使用者看到的文案」對照表。

### `sa/{功能}-design.md`

- 要新增／修改哪些檔，各自照哪個既有檔案寫，差在哪
- 前後端介面契約（欄位名、型別、意思），先在質詢輪拍板再寫死
- 資料表異動的 SQL 草稿，標「確認後才可執行」
- 缺口清單與對應 `Q-XX`

### Python／FastAPI 專案另產

`sa/{功能}_test_skeleton.py`：pytest 骨架，分 API 層與 Domain 層，測試方法留 TODO，交給 QA 填。

## 交件前自己對一次

- [ ] 掃描表每個名稱都有檔案:行號
- [ ] 設計 grill 已做，紀錄已存
- [ ] PM 的每個 Scenario 都有對應的技術版 Scenario，縮減的寫明原因
- [ ] 每個 feature 檔尾都有錯誤碼對照表
- [ ] 技術設計有檔案清單、介面契約、缺口清單
- [ ] 交件摘要寫：產物路徑、每個畫面的型態、資料實查結果、還沒拍板的 `Q-XX`。下游開工前**必讀 grill 紀錄**
