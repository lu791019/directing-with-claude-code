# qa-flow：自動化測試流程

QA 驗的是「程式照 SA 規格動作」。全綠只是起點，不是完工。

## 開工前

讀 `PROJECT_PROFILE.md`：測試框架、跑全部測試的那一行指令、E2E 工具、覆蓋率門檻、測試站網址、名詞表。

- E2E 寫「（無）」→ 整層不做，寫進計畫書的「不驗清單」。
- E2E 空白 → 問使用者要不要做、用什麼工具，不自己挑。
- 測試框架寫「（無）」→ 這次就是建立測試的時機，框架選擇開 `Q-XX` 給建議，拍板後建立。

文件類產物（計畫、報告、紅綠紀錄）寫 `qa/`；測試程式碼放專案既有的測試目錄。

主要依據是 SA 產物（技術版 Gherkin、grill 紀錄、技術設計、測試骨架），PM 產物當背景。沒有 SA 產物時退回 PM 的 Gherkin，並註明；連 PM 產物都沒有，就停下來問。

## 和實機驗收的分工

QA 用自動化測試驗「行為符合規格」；實機驗收是人照驗收單在真實站台操作、截圖。兩者不能互相代替，QA 全綠之後才值得做實機驗收。

找到缺陷只回報（重現步驟、預期與實際、可能的檔案），不自己改產品程式碼。

## 一、掃描

答得出這四題才往下：

- 專案現在用什麼測試框架、怎麼跑（沿用，不換）
- 測試目錄與命名慣例、既有 fixture、測試資料庫怎麼起
- **怎麼確認測試全部被收進來**：多數框架少收一個檔不會報錯
- SA 的每個 Scenario 該落在哪一層、為什麼

## 二、測試計畫（先過人）

`qa/{功能}-test-plan.md`：

1. 來源文件清單
2. 測試範圍，以及**不驗清單**：不驗什麼、為什麼、依據哪份文件。不驗可以，默默不見不行
3. Scenario × 層級對照表：每個 Scenario 至少一個測項；標 `@e2e` 的一定有 E2E 測項
4. 測試環境確認：框架跑得起來、測試資料庫起得來、E2E 站台連得到
5. 待確認事項（沒有寫「無」）
6. 安全性測試預設不在範圍內；要做的話範圍與授權對象寫清楚、拍板後才做

結尾請使用者確認，回「確認開始」才寫測試。

## 三、寫測試

| 層 | 驗什麼 | 規矩 |
|---|---|---|
| 單元 | 業務邏輯、邊界值、例外路徑 | 斷言業務狀態，不只斷言 mock 被呼叫 |
| 整合 | 模組之間的接縫 | 資料層測試接真的資料庫（本機或容器） |
| API | 狀態碼、回應形狀、錯誤碼對文案 | 驗證失敗、權限不足、狀態衝突都要有測項 |
| E2E | 正常路徑上看得到的結果 | 驗行為，不只驗元素存在；從正常入口走；寫入類絕不對正式環境跑 |

- 文件沒定義的行為不發明測項，開 `Q-XX`。
- 紅燈的原因要是斷言失敗或功能不存在；環境壞掉的紅是假紅。
- 防重送、競態這類情境，mock 幾乎沒有延遲，要讀程式加實測兩邊驗。
- 不改、不停用、不刪既有測試換綠燈。
- 每筆紅轉綠記進 `qa/{功能}-tdd-log.md`。

## 四、四道真實環境驗證（完工定義）

1. **依賴真的裝了**：每個被 mock 掉的外部依賴，用一行真實指令證明它存在、能用。
2. **真路徑跑過**：每條會寫資料的主流程，至少一條不 mock 關鍵依賴的測試真的跑過。
3. **收案數對得上**：實際收進來的測試數，逐層對計畫書的測項數。
4. **突變抽驗**：每組新測試至少一次，故意弄壞一行產品程式碼，測試必須變紅；還原後回綠。全綠代表測試沒鎖住東西，重寫斷言。

哪一道沒過，對應測項只能標「已完成未驗證」或「受阻」，不能標通過。

## 五、測試報告

`qa/{功能}-test-report.md`：

- 四個數字：總數／綠／紅／略過；失敗的測試名稱全列
- 三態分開算：通過／失敗／未驗證，加起來要等於計畫的測項數
- 每一列附執行指令和輸出關鍵行；沒有證據的「通過」算未驗證
- 自問三題：行為斷言真的跑了嗎？收案數對上了嗎？mock 以外的真路徑跑了嗎？
- 缺陷清單；覆蓋率有門檻就附實際數字

交件時寫：四個數字、報告路徑、缺陷幾條、還沒拍板的 `Q-XX`，並註明下一步是實機驗收。
