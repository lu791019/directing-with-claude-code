# UX 黑白箱試跑

讓 AI 測試員照任務操作真實畫面或雛形，再由你（協調窗）核對、去重、出報告。

你是**協調窗**。測試員在各自的 session 裡跑，你負責設計、派工、回收、裁定。
方法的依據與試跑心得在 `references/method.md`，要調整編制或判準前先讀。

需要 Claude Code、Claude in Chrome 擴充功能（黑箱操作瀏覽器）與 Python 3（兩支腳本）。沒有 Chrome 擴充功能時，先請使用者裝好，或只派白箱。

三件事決定這套方法成不成立，全程都要守住：

1. **證據等級是「檢查發現」。** AI 只能說畫面有沒有某個性質，不能說使用者會不會怎樣。「好不好用、看不看得懂」只能列入「待真人測試」。報告不得寫「使用者會卡住」，要寫成畫面事實。
2. **測試員自報的不算數。** 每條問題都要核對，規則遵守要看逐字紀錄。試跑中有不少回報不屬實或只有部分屬實。
3. **憑證與寫入由人決定。** 你不讀含密碼的檔案、不輸入帳密、不替人登入，動資料庫或共用環境前先問。

## 先判斷在哪個階段

看目前資料夾與使用者的話：

| 狀況 | 走哪段 |
|---|---|
| 還沒有 `trial.json` | 一、設計 |
| 有 `trial.json`，測試員還沒跑 | 二、開 session |
| 測試員都寫好回饋檔，或使用者說跑完了 | 三、回收分析 |
| 使用者只帶來一批回饋檔 | 直接到三，缺的設定用問的 |

中途接手時，先讀 `trial.json` 和 `_coordinator/status.md`。

**受測物是還沒開發的雛形時，先讀 `references/prototype-gate.md`。** 三個階段照走，差別是白箱先跑、不做故意犯錯、測試前要準備複本、多一種判定「mock 限制」。雛形報告不能當上線依據，實機還要再跑一次。

**功能開發完、要交 PM 驗收前，先讀 `references/live-gate.md`。** 它寫什麼時候跑、誰做什麼、怎麼帶入雛形關結果、怎麼交給 PM。

## 一、設計測試

先自己查，再問人。需求單、工單、ADR、README 查得到的不要問。查不到的集中問一次：

- 受測功能、範圍外的部分、版本（commit 或部署日期）
- 站台網址，誰負責起站
- 登入方式、用什麼帳號與角色，**由使用者本人登入**
- 能寫入哪些資料，測試資料怎麼隔離（每位測試員一份，名稱加前綴）
- 白箱要對照什麼：規範文件、設計稿、平台版型
- 已知問題清單，來自前次測試或既有缺陷
- 有沒有會影響別人的動作：寄信、通知、改共用設定、背景作業

問完依序做：

1. 讀 `references/task-design.md`，寫任務卡與故意犯錯清單。任務只描述情境，不教操作，也不能出現按鈕文字。
2. 讀 `references/pitfalls.md`，把適用的環境陷阱寫進 `trial.json`。
3. 照 `assets/trial.example.json` 與 `references/trial-fields.md` 建 `<測試根目錄>/trial.json`。預設編制 4 位：L1、L2、L3、W1，模型照 `references/method.md`。版本查不到就寫「未驗證」，列進開工檢查。
4. 把計畫存成 `<測試根目錄>/plan.md` 並給使用者看，內容只要：測什麼、誰跑、會寫入什麼、預估時間、還原方式。時間參考 session-guide 的估計。等使用者同意。
5. 產生資料夾：

   ```bash
   python <skill 目錄>/scripts/scaffold_trial.py <測試根目錄>/trial.json
   ```

   會產生各測試員的 `prompt.md`、`tasks.md`，以及 `_coordinator/launch.md`、`status.md`。

## 二、開 session

讀 `references/session-guide.md`，照它帶使用者走。重點：

1. **開工檢查**：站台版本對、測試資料建好、瀏覽器連得上、使用者已登入、Chrome 分頁停在正確帳號。
2. **開 session**：環境有 `start_session` 工具且使用者同意，就由你開；沒有就把 `launch.md` 的指引卡一張一張給使用者，每位測試員一個新 session，資料夾、模型、第一句話都寫死。
3. **跑的過程**：測試員來問時，只回答帳號、測試資料、規則解釋，不教操作。教了就污染結果。
4. 每位結束就更新 `status.md`。

寫入授權要在派工前寫進 `trial.json` 的 `authorized_writes`。事後轉達授權曾被權限機制判定為繞過，見 pitfalls。

## 三、回收分析

讀 `references/analysis.md`，照順序做：

1. 確認每位都有回饋檔。
2. 跑稽核，看規則遵守、實際時間與被擋的動作：

   ```bash
   python <skill 目錄>/scripts/audit_transcripts.py <測試根目錄>/trial.json
   ```

3. 逐條核對每筆回報，判「屬實、部分屬實、不成立、工具問題、未能核對」，雛形另有「mock 限制」，並標證據層級。**連按、按鈕換位、沒提示卻可能已寫入的回報，要親自重做並查實際寫入，只讀碼定不了。** 這類條目實測被低估過。
4. 去重合併，重新編號，定嚴重度。嚴重度只看可觀察後果：任務做不做得完、有沒有不可逆的影響。
5. 算精確率，寫報告。格式照 `assets/report-template.md`。
6. 列「待真人測試」，以及有沒驗到的範圍。沒驗到要明講，不要省略。
7. 清理：列出測試資料與還原方式，使用者同意才動。

**修不修由使用者裁示。** 這份報告只回報事實，不自行改程式。

## 收尾

交付時說清楚：報告路徑、高中低各幾條、最該先處理的兩條、沒驗到什麼、測試資料還在不在。
