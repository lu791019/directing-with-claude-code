# 實機關

功能開發完、要交 PM 驗收前讀這份。其餘步驟照 SKILL.md。試跑心得在 `method.md`。

目的是在 PM 真人驗收前，先抓實作帶出來的問題：寫入後果、連按、後端驗證、錯誤訊息、真實資料下的版面。QA 對照規格驗有沒有做到，這關看沒讀過規格的人走不走得下去，兩者不互相取代。

## 什麼時候跑

新畫面或流程改動才跑，判準和雛形關相同。小異動、純後端不跑。使用者說不跑就記在交接裡。

時機是 QA 通過、部署到測試站之後，交 PM 驗收之前。

站台要接真實 API。資料全走 mock 或 Playwright 攔截時，寫入後果驗不到，等串接後再跑。

## 誰做什麼

| 誰 | 做什麼 |
|---|---|
| 工程師 | 提供站台與帳號、本人登入、同意寫入範圍、決定修不修 |
| 主對話（協調窗） | 設計任務、開 session、核對、出報告，不改程式 |
| 測試員 | 在各自的 session 照 `prompt.md` 操作 |
| PG 角色 | 修工程師決定要修的條目，修完照常回 QA |

## 準備

照 SKILL.md「一、設計測試」。實機關另外注意：

1. 用測試站，不用正式機。`whitebox.revision` 寫部署的 commit，查不到寫「未驗證」。
2. 編制用預設 4 位。L2 的價值在犯錯路徑，實機才看得到。
3. 測試根目錄放 repo 外。放在 repo 裡，黑箱測試員會載入專案的 CLAUDE.md，等於先看過規格。
4. W1 的 `repo_path` 是受測 repo，`files` 放這次改動的畫面與呼叫鏈，`standards` 放 SA 的 `.feature` 與平台規範。

有跑過雛形關時，把結果帶進來：

- 雛形關的任務卡沿用，再補故意犯錯與前後依賴。
- 定案雛形與雛形關報告放進 W1 的 `standards`，對照實作有沒有偏離。
- 決定不修的條目寫進 `known_issues`，只寫現象。
- 標「mock 限制」的條目到實機才驗得到，和本功能有關的排進任務。

## 修正

修不修由工程師決定，報告只回報事實。

- 高、中級處理完才交 PM：修掉，或和 PM 講定轉單。低級不擋。
- 修完由協調窗照報告的重現步驟親自重驗。改到流程時，再派一位 L1 跑受影響的任務，不用整輪重跑。

## 交給 PM

報告放進 case 的 QA 資料夾，例如 `spec/{case-name}/qa/ux-trial-{YYYYMMDD}/`。交驗收時告訴 PM：

- 高中低各幾條，修了哪些，沒修的理由
- 待真人測試的項目
- 沒驗到的範圍

這份報告是檢查發現，不能取代 PM 真人驗收。
