# 任務卡怎麼寫

任務卡決定測得到什麼。寫壞了，測試員會照著答案走，結果看起來全過。

## 原則

**只寫情境與目標，不寫操作。** 不出現按鈕文字、選單名稱、步驟順序。

- 不好：點「編輯版面」，拖動卡片，按「儲存為個人版面」。
- 好：再調整一次排列，這次只存給自己看。

**用使用者的話，不用系統用語。** 如果任務用了畫面上的詞，等於替測試員找到入口。把用語差異留著，測試員找不到才測得出命名問題。

界線：**控制項名稱不能用，內容值可以用。** 按鈕、頁籤、欄位標籤、快選鈕的文字不能出現；要查的日期、品名這類資料值可以寫。寫之前先看一次畫面文字，避開它們。

**一個任務一個目標，有明確終點。** 測試員要能判斷完成了沒。

**涵蓋完整來回：** 建立、確認留下、改一半反悔、回到原狀、交給別人。

**前後要有依賴。** 讓後面的任務用到前面的結果，才測得到資料有沒有留下。

## 建議結構

| 區塊 | 內容 | 數量 |
|---|---|---|
| 背景 | 一句話：你是誰、想做什麼 | 1 |
| 主要任務 | 核心流程，照真實順序 | 3～5 |
| 反悔任務 | 做到一半放棄，確認回到原狀 | 1 |
| 取得結果 | 把成果交給別人、匯出、分享 | 0～1 |
| 故意犯錯 | 主要任務都寫進回饋檔後才做 | 5 |
| 權限任務 | 換低權限身分，看被擋時畫面怎麼說 | 視需要 |

## 查詢與報表型功能

沒有寫入時，結構這樣換：

| 區塊 | 寫法 |
|---|---|
| 主要任務 | 給一個要回答的問題，答案要從畫面找出來 |
| 反悔任務 | 條件改一半，回到起始狀態，確認條件與結果都復原 |
| 取得結果 | 匯出或列印，確認內容對應到剛才的範圍 |
| 權限任務 | 只有單一角色時略過，報告註明沒測 |

測試員沒有專屬資料時，`sandbox` 留空即可。要注意兩件事：

- 下載的檔案測試員讀不到內容，由你事後檢查。
- 唯讀頁面可能開到可寫入的視窗。設計時讀程式確認，把那些動作列進 `dont_click`。

## 雛形

受測物是雛形時不做故意犯錯，也不靠前後依賴。差異見 `prototype-gate.md`。

## 故意犯錯

主要任務結果寫完才做，否則會汙染主要任務的紀錄。五項都要有結果，做不到也要寫原因。從下列挑五種：

- 把東西拖到畫面外或不合法的位置
- 全部清空後儲存，或必填留空送出
- 儲存時連按多次，**雙擊會換畫面的按鈕**
- 有未儲存修改時離開或重新整理
- 超過上限：字數、數量、最大最小尺寸
- 特殊字元、超長名稱、貼上大量文字
- 條件顛倒，例如起訖日相反

在多人共用的站台上，會產生大量查詢或大量下載的項目，改由你代測，或降低次數。

## 已知問題清單

已知問題要給測試員，否則會重複回報。但寫的方式會影響結果：

- **只描述現象，不要寫出解法或操作方式。**
  實例：清單寫了「雙擊或按 Enter 可以加入卡片」，結果測試員直接用雙擊，「入口找不找得到」就沒測到。
- 改寫成：「卡片的鍵盤操作目前不完整。」
- 寫明「行為不一樣才報」。

## 按鈕會跳原生對話框時

Chrome 工具操作不了原生 `prompt`、`confirm`，分頁會卡死。把這些動作列進 `native_dialog_actions`，測試員找到按鈕就停，你事後代測。

要注意，這樣測不到按下去之後的部分，報告要寫明。

## 資料隔離

- 每位測試員一份獨立資料，名稱加前綴，例：`AIBB-L1`。AIBB 代表 AI 黑箱。
- 同一帳號多人共用時，主題、最近紀錄這類個人狀態會互相干擾，寫進 `not_issues`。
- 刪除動作不要讓測試員做，改由你代測。留下的資料才能核對。
