## 開發流程文件

接到開發任務時，依序產出三份文件（template 見 `templates/dev-workflow.md`）：
1. **實作前**：專案根目錄產出 `implementation_plan.md` + `task.md`，等使用者確認
2. **實作中**：按 task.md 逐項執行，遵循反饋循環，逐步勾選完成
3. **收尾**：產出 `walkthrough.md`，並依 template §3 同步更新 PLAN.md + GUIDE.md
4. **持續**：需求/架構變更時也須同步更新（觸發條件見 template §3）
5. **交接**：寫或改 HANDOFF 前先讀 `handoff/SKILL.md`（讀者是決策者；寫什麼／不寫什麼；150 行或 25KB 或換階段就封存／開新檔；憑證只寫位置不寫值）
6. **讀交接**：新 session 開場用 `@HANDOFF.md` 帶入；使用者只用文字說「讀 HANDOFF」時，回覆前必須先打開全文，不可只憑檔名或記憶作答
7. **分輪派工與黑箱試跑**（所有開發的預設）：開發任務一律照 `dispatch-round` skill 編排（主線編排與複驗、子代理實作、高風險的測試由另一個代理寫）；有新畫面或流程改動的，交件之前先跑 `ux-blackbox-trial`（值不值得跑照該 skill 的判準；純後端、小異動不跑，要記下理由），高、中級的檢查發現處理完才交件

## 反饋循環（Feedback Loop）— 每次開發任務必須遵守

每次撰寫或修改程式碼後，必須完成以下驗證循環，直到所有檢查通過為止：

1. **執行**：執行你寫的程式碼，確認它能正常運作
2. **測試**：運行專案的測試套件（偵測並使用專案的測試框架）
3. **檢查**：執行 linter / type checker，確認無錯誤
4. **修復**：如果上述任一步驟失敗，修復問題後回到步驟 1
5. **完成**：所有步驟通過後才能視為任務完成

### 規則
- 不要跳過驗證步驟，即使你「確定」程式碼是正確的
- 測試失敗時，閱讀錯誤訊息、理解根因、修復後重跑
- 如果專案沒有現成測試，先為你修改的功能寫測試再驗證
- commit 前必須確保所有測試通過
- 動手前定風險等級與驗收條件（Given/When/Then，至少一條邊界情境），測試深度依等級走，細則見 `testing.md`
- 修 bug 先寫能重現它的測試再修，測試永久留下；寫程式的 agent 不改測試（派工標 `TESTS=locked`，hook 擋）
- 回報不只給通過率：失敗項要標風險等級，驗收條件逐條附證據
